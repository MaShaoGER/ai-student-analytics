# ADR 0001：AI 只产出受限分析计划，不产出 SQL

- 状态：已采纳（2026-10-18）
- 背景材料：`output/ai-review/OVERALL-ai-review.md`（A 段）、[AI 第一阶段边界](../ai-phase1.md)、[演示问题与基准](../demo-questions.md)（审计材料在 `.gitignore` 的 `output/` 下，仅本地可读）

## 决策

模型（百炼/智谱/OpenAI）只输出**受限的结构化分析计划**：指标、维度、筛选、排序、条数、图表类型、理由或澄清问题。后端用 Zod 重新校验，再由参数化查询或固定统计 SQL 执行。模型不接触 SQL 文本、不接触学生明细，也不生成最终数字。

执行链路：`converse` 选动作 → 服务端校验/补全计划 → DuckDB 执行 → 程序计算数值摘要 → 模型只做措辞解释（且正文中的阿拉伯数字被拦截）。

## 背景

- 教育场景对“数字从哪来”要求极高；一旦允许模型写 SQL，错误 SQL、幻觉字段、注入和越权读取的风险不可控。
- 项目路线图明确排除“通用 Text-to-SQL”，只接入三个指标、两个维度和既有图表工具（见 `AI学生数据分析系统开发路线图.md`）。
- 审计复核发现旧实现里模型决策会被中文正则二次覆盖（`conversation.ts` 的 `inferGoal` 与响应展示推断存在两套实现），说明“模型只说语义、代码只补空值”的边界本身也需要收紧，而不是把决策权交给 SQL 生成。

## 备选方案

1. **Text-to-SQL（模型直接生成查询）**：灵活，但无法保证只读、白名单与样本阈值；审计难以复现，演示风险最高。否决。
2. **模型直接生成表格/数字**：最容易“看起来对”，但与“数字不可编造”的底线冲突。否决。
3. **完全规则化（不用模型）**：最安全，但自然语言覆盖窄、演示缺少 AI 差异点，且澄清能力差。否决。
4. **受限计划 + 本地执行（本决策）**：牺牲一部分灵活性，换取可测试、可审计、可回滚。

## 后果

- **正面**：注入/越权面收敛到“字段与枚举”；每个数字都能在本地复算；计划可写入审计并与 `PROMPT_VERSION` 关联；评测集可以只比对“动作/指标/维度”，不依赖模型输出文本。
- **代价**：新增能力（出勤、作业提交率、个体明细）必须先开发适配层，模型不能“自己会”；能力扩展节奏由代码决定，不由 prompt 决定。
- **约束**：模型只能看课程/学期标签与聚合结果；超出能力必须澄清（见 [AI 评测基线](../ai-eval-cases.md) 的边界用例）；prompt 改动需要提升 `PROMPT_VERSION` 并重跑评测。
- **演进**：若未来要开放更多指标，优先扩展 `AnalysisPlan` 的受限字段与工具注册表，而不是放开 SQL 生成。
