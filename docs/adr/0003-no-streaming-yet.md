# ADR 0003：暂不做流式输出，保留一次性 JSON 响应

- 状态：普通问答继续采纳；综合分析于 2026-10-19 调整为阶段事件 SSE（见下文）
- 背景材料：`output/ai-review/human-ai-interaction.md`（P1-1 与“小改 vs 大改”，本地审计材料）、[AI 第一阶段](../ai-phase1.md)、[AI 图表能力扩展](../ai-chart-capabilities.md)

## 决策

`POST /api/chat` 继续返回**一次性 JSON**（`ChatResponse`：文字、facts、artifact、planning），不引入 SSE/逐字流式。等待体验用**阶段文案**缓解（“正在理解问题… / 正在查询数据… / 正在组织解读…”），而不是流式 token。

## 背景

- 当前一次提问最多两次模型调用（规划 + 解读），结果还需要本地 DuckDB 查询与图表数据组装；响应是“查询结果 + 计划 + 解释”的整体，无法只把模型 token 流给前端。
- 流式需要改协议（SSE 或分块 JSON）、处理中途取消与半成品结果、改造前端消息状态机，并重新定义审计（何时算一次请求）与预算（流中断如何结算）。属于 M 级改动，收益集中在“感知速度”。
- 审计确认演示中真正的信任缺口不是“字出得慢”，而是“来源、依据、筛选、失败归因看不到”；这些都已通过 `facts`、`planning`、错误码与筛选提示以更低成本补齐。

## 备选方案

1. **真流式（SSE）**：逐字出文，感知最快；但结果卡要等查询完成才能画图，文字先出反而让“数字后到”更割裂；改造面大、演示风险高。暂缓。
2. **分阶段 JSON（先返回“已理解/正在查询”消息）**：需要双请求或轮询，状态机复杂，收益有限。否决。
3. **乐观等待 + 阶段文案（本决策）**：不改契约，只改前端文案与停止/重试语义；失败时不吞已得结果。
4. **后端预热/缓存**：对重复固定问题有效，但 golden case 本就本地短路，收益集中在慢查询而非模型。不合入本决策。

## 后果

- **正面**：`/api/chat` 契约稳定，评测、审计、前端错误处理都简单；取消语义（499）与预算结算清晰；改动小、可快速回归。
- **代价**：长回答等待期只有阶段文案，用户无法“边出边读”；模型首 token 延迟直接体现在体验里；无法展示“正在生成”的细粒度进度。
- **约束**：单次响应受 20 秒模型超时与请求大小限制；等待超过 10 秒应给阶段变化与可停止提示；停止后要明确“已停止，可重试”，避免用户误以为系统崩溃。
- **重新评估条件**：出现以下任一情况再启动 SSE 改造——(a) 平均等待 >8 秒成为主要投诉；(b) 需要“先出文字、后补图表”的交互；(c) 需要跨请求的会话持久化。届时需同步修订 `ChatResponse` 契约、审计阶段字段、取消与预算结算规则，并更新演示预案。

## 2026-10-19：综合分析的阶段事件

第二阶段引入受控多步工具调用。综合分析请求使用 `mode: "comprehensive"`，并可通过 `Accept: text/event-stream` 订阅真实步骤；普通问答继续一次性 JSON，未声明 SSE 的综合分析客户端仍接收最终 JSON。

- SSE 只传递 `step`、`result`、`error`，不逐字输出模型文本，不公开内部推理。每个流有独立 requestId，步骤有独立 id。
- 鉴权、同源、限流及输入验证发生在建立流之前；开始执行后失败使用安全的终结 error 事件，不依赖已经发出的 HTTP 状态码。
- 每个请求最多一个终结事件。读取器检查 UTF-8 分块、完整帧、请求归属和提前断流；页面另用 AbortController 与请求代次拒绝旧结果。
- 断开、停止和总时间限制传递到模型及 DuckDB。取消不继续调用工具；预算按实际发生的每次模型请求预留和结算。
- 分析审计仍按一次用户请求记录，附固定操作名、状态与耗时；不记录问题、模型正文、检索片段和原始数据行。

该调整用于展示真实执行过程；普通问答等待提示改为中性“正在处理分析请求”，不再按定时器假定执行阶段。
